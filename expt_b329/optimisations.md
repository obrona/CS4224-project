### Prev: expt_b300 (grid base)

Cell 329 (T1 mode 1 `fn`, mask 13) of the 2^4 x 3 workload-B ablation (`ablation/README.md`, "Workload B"); every cell's factor levels are in `ablation/manifest_b.csv`. Generated by `ablation/generate.py --side b` from `ablation/template/`: change the template and regenerate rather than editing this directory.

`transactions/` and `explain/` are byte-identical to `expt_a329`'s, the workload-A cell with the same factor levels, and `run.sh` differs from `expt_a329`'s only in the node pin (`--nodelist=xcnf[17-21]`, the B-side node set: disjoint from A's and shared by every B cell), the mail user and the `WORKLOAD` default (`B`).

Everything not listed below is therefore the grid's shared reference, as on workload A: the schema, distribution, indexes, T2, T3, T4, T8, T9 and server parameters of the workload-A base design (formerly `expt_a3`, see git history), `TEAM_ID` default 4 and `PGPORT` derived from `TEAM_ID`. `run.sh` also records plans outside the timed benchmark.

Enabled factors:

| Factor | Description |
| ------ | ----------- |
| `t5_routing` (bit 1) | T5 routing: T5 looks up `order_merchant_map`; T1 inserts the map row; `run.sh` creates, distributes, fills and truncates `order_merchant_map` |
| `t7_routing` (bit 4) | T7 routing: T7 is `expt_b7`'s: it looks up `product_merchant_map` before `BEGIN` and routes its two `UPDATE`s; `run.sh` creates, distributes, fills and truncates `product_merchant_map` |
| `shards8` (bit 8) | Eight shards: `run.sh` sets `citus.shard_count` to `CITUS_SHARD_COUNT` (default 8, Citus's own default is 32) in the session that distributes every table, and records it in `config.txt` |
| `t1_mode=fn` (m=1) | T1 delegation: T1 is the `place_order` distributed function, called outside a transaction block; `run.sh` creates and distributes the function |

T1's `place_order` is `expt_a323`'s with step 6 (`merchant_daily_sales` upsert) removed from the function body. The signature, the pgbench-side statements and the rest of the body are unchanged, and the remaining steps keep the original numbering.
Step 4 still has `RETURNING total_amount, created_at INTO v_order_total, v_created_at`, although only step 6 read them.
